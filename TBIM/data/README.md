# ชุดข้อมูลสัญลักษณ์งานเขียนแบบ TBIM (TBIM-SYM)

ชุดข้อมูลสัญลักษณ์และสัญกรณ์ (notation) สำหรับแบบก่อสร้าง ในรูปแบบที่โปรแกรมอ่านได้ สำหรับโปรแกรม BIM ของไทยชื่อ **TBIM**
ยึดแนวปฏิบัติของไทยเป็นหลัก และเก็บรูปแบบของต่างประเทศ (ISO, IEC, US NCS/NECA, NFPA, GB, JIS, DIN ฯลฯ) ไว้เป็น "โปรไฟล์ภูมิภาค" ของระเบียนเดียวกัน

> **ที่มา:** สร้างจากบันทึกการค้นคว้า 6 ฉบับใน `TBIM/research_notes/สัญลักษณ์งานเขียนแบบสำหรับ TBIM/` เท่านั้น (ค้นคว้าเมื่อ 2026-09-27) **ไม่ได้ค้นเว็บเพิ่ม**
> URL ทุกตัวในแคตตาล็อกคัดลอกมาจากบันทึกโดยตรง (`validate.py` ตรวจให้) และไม่มีเลขมาตรฐานใดที่ไม่ได้ปรากฏในบันทึก

> **ข้อควรทราบเรื่องชื่อ:** "TBIM" เป็นชื่อของ **สมาคม TBIM (Thai BIM Association, tbim.or.th)** อยู่แล้ว สมาคมนี้เผยแพร่ Thailand BIM Object / Construction Material Guideline ควรประสานงานกับสมาคม (อาจขอให้รับรองแคตตาล็อกนี้) หรือเปลี่ยนชื่อโปรแกรม

## 3. ความหมายของสถานะ (`status`)

| ค่า | ความหมาย |
|---|---|
| `standard` | กำหนดโดยกฎหมายหรือมาตรฐานที่มีเลขที่ (มอก., มยผ., วสท., กฎกระทรวง, ISO, IEC, NFPA, GB ฯลฯ) |
| `agency` | กำหนดในคู่มือหรือแบบมาตรฐานของหน่วยงาน (กรมทางหลวง, ทช., กรมชลประทาน, กรมที่ดิน, กรมแผนที่ทหาร) มีผลกับงานของหน่วยงานนั้น |
| `observed_practice` | พบในแบบจริงของไทย (เช่น ชุดแบบขออนุญาตที่อ่านได้ทั้งฉบับ) หรือในแหล่งการสอน/ผู้ปฏิบัติที่อ้างในบันทึก ไม่มีมาตรฐานกำกับ |
| `unverified` | มาจากความรู้ทั่วไปหรือการอนุมานในบันทึก ยังไม่ได้ยืนยันกับแหล่งที่เปิดอ่านได้ |

สถานะคัดลอกตามที่บันทึกระบุอย่างตรงไปตรงมา:
- **ทุกแถวของแคตตาล็อก MEP ไทย (125 แถว) เป็น `unverified`** เพราะ `th_mep.md` ระบุว่ามาจากความรู้ทั่วไปเกี่ยวกับแผ่นสัญลักษณ์ของไทย และยังไม่ได้ตรวจกับ PDF ใดเลย บางอักษรย่อ (เช่น CW/HW/S/W/V, MDB/LP, FDC) มีแหล่งยืนยันและระบุไว้ใน `description` / `sources` แต่รูปทรงสัญลักษณ์ยังไม่ยืนยัน
- สัญลักษณ์สถาปัตย์ส่วนใหญ่เป็น `observed_practice` จากแผ่นสัญลักษณ์ A0-01 ของชุดแบบขออนุญาตจริงหนึ่งชุด (อ่านได้เฉพาะชั้นข้อความ จึงไม่รู้รูปทรงที่วาดจริง)
- ระเบียนที่ไม่มี URL แหล่งที่มาจะมี `source_note: "general practice (unverified)"` เสมอ
- `region_profiles[]` แต่ละรายการมี `status` ของตัวเอง (เช่น ระเบียนไทยเป็น `observed_practice` แต่โปรไฟล์ GB เป็น `standard`)

## 4. คำอธิบายฟิลด์ของระเบียนสัญลักษณ์ (`symbols[]`)

| ฟิลด์ | คำอธิบาย |
|---|---|
| `id` | รหัสถาวร เป็น ASCII ไม่ขึ้นกับภาษา รูปแบบ `ภูมิภาค.หมวดงาน.ชื่อ` เช่น `TH.ARCH.SECTION_MARK`, `INTL.ELEC.PUSH_BUTTON` **ห้ามเปลี่ยนหรือนำกลับมาใช้ซ้ำ** |
| `version` | เวอร์ชันของระเบียน (semver) |
| `discipline` | ARCH, STR, ELEC, ELV, FA, PLB, SAN, FP, HVAC, GAS, CIVIL, SURVEY, GENERAL (ต้องตรงกับส่วนกลางของ `id`) |
| `category` | reference_marker, tag, level, grid, line_type, hatch, device, fixture, valve, equipment, notation, dimension, plan_symbol, schedule, sheet |
| `name`, `description` | `{th, en}` |
| `abbreviations` | อักษรย่อ/ป้ายที่ใช้ เช่น `["D", "ป"]` |
| `aliases` | ชื่อเรียกอื่น `{th:[], en:[]}` เช่น ป้ายในแผ่นสัญลักษณ์ "แสดงรูปตัดที่ _" |
| `status`, `status_note` | ดูหัวข้อ 3 |
| `source_code` | รหัสแถวเดิมในบันทึก (เฉพาะ MEP) |
| `lineage` | สายรูปแบบของสัญลักษณ์ (US / IEC / local ฯลฯ) |
| `region_profiles[]` | รูปแบบตามภูมิภาค: `region` (TH, ISO, IEC, US_NCS, US_NECA, NFPA, US_AWS, US_ACI, US_ASHRAE, ISA, JIS, GB, DIN, BS, AS, KS), `status`, `geometry_notes`, `standards`, `sources`, และอาจมี `svg_path`, `nominal_size_mm`, `symbol_ref` (เช่น IEC S00473, ISO 7010 E001) ระเบียน `TH.*` ต้องมีโปรไฟล์ `TH` เสมอ |
| `geometry` | ดูหัวข้อ 5 |
| `text_fields[]` | ช่องข้อความ: `name`, `source` (`element_property` = อ่านค่าจากองค์ประกอบ/วิวที่ลิงก์ผ่าน `query` แบบ `{{...}}` ของ Bonsai; `user` = ผู้ใช้พิมพ์เอง), `format` (regex), `text_style` (TH-1.8…TH-7), `required`, `default` |
| `notation_grammar[]` | ไวยากรณ์ของสัญกรณ์ข้อความ: `regex`, `examples` (ทุกตัวอย่างต้อง match ทั้งสตริง), `groups`, `normalization`, `status` เช่น เหล็กเสริม `4-DB16` / `RB9@0.20`, ระยะสถานี `0+000`, ค่าระดับ `+0.20`, เลขแผ่น `A0-01`, ระวางกรมที่ดิน `5136II9214` ตัวอย่างที่แต่งขึ้นเองมี `examples_note` กำกับ |
| `ifc_mapping` | `entity` (IfcAnnotation / IfcCurveStyleFont / IfcFillAreaStyleHatching …), `predefined_type` (IfcAnnotationTypeEnum ของ IFC4.3; IFC4 ไม่มีฟิลด์นี้), `object_type` (= `id`), `host_relation` (IfcRelAssignsToProduct), `host_ifc_classes`, `pset` (`TBIM_Annotation.SymbolId`) |
| `classification[]` | ลิงก์ระบบจัดหมวด `{system, code, uri, …}` (ยังว่าง ดูหัวข้อ 8) |
| `standards[]` | `{code, title, edition, clause?, relation, note?}` `relation`: defines / governs_content / lineage / drafting_reference / related |
| `sources[]` | `{url, title, evidence, supports?}` `evidence`: full_text, search_snippet, schema_introspection, source_code, not_read |
| `source_note` | `"general practice (unverified)"` เมื่อไม่มี URL สนับสนุน |
| `verify_against[]` | PDF ต้นฉบับที่บันทึกพบแต่เปิดอ่านไม่ได้ ใช้ตรวจสอบภายหลัง |
| `precedents[]` | ตัวอย่างอ้างอิงเชิงออกแบบ (เช่น Bonsai) ใช้อ้างอิงเท่านั้น ห้ามคัดลอก |
| `related_ids[]` | ระเบียนที่เกี่ยวข้อง |
| `licence_note` | ข้อควรระวังด้านลิขสิทธิ์เฉพาะระเบียน |

## 5. เรขาคณิต (`geometry`)

- `units`/`scaling`: `mm_paper` + `paper` = ขนาดคงที่บนกระดาษ ย่อขยายตามมาตราส่วนวิว (annotative) / `mm_model` + `model` = ขนาดจริง (โคมไฟ หัวจ่ายลม ลายแรเงา เครื่องหมายจราจรบนพื้นทาง)
- `insertion_point` = `[0,0]` ใน frame ของสัญลักษณ์ (ปกติคือจุดศูนย์กลาง)
- `nominal_size_mm` + `size_basis`: `source` (ขนาดจากบันทึก), `region_profile` (ยืมจากโปรไฟล์ เช่น ลูกศรทิศเหนือ GB Ø24), `tbim_proposed_default` (ค่าเริ่มต้นที่ TBIM เสนอ เช่น วงกลมอ้างอิง Ø10 มม. ซึ่งไม่ใช่ค่าจากแหล่งไทย), `unknown`
- `svg_path`: สตริง `d` ของ SVG (แกน x ขวา y ลง, หน่วยตาม `units`) **มีเฉพาะเมื่อบันทึกให้มิติพอจะวาดได้** ถ้าไม่พอจะใช้ `redraw_description` แทน `svg_basis`: `notes` (มิติทั้งหมดจากบันทึก), `notes_partial` (บางมิติ TBIM เสนอ), `tbim_proposed`
- `glyph_text`: ตัวอักษรคงที่ในสัญลักษณ์ (เช่น "S", "FACP"); ข้อความที่เปลี่ยนตามองค์ประกอบอยู่ใน `text_fields`
- `line_pattern` (สำหรับ line_type): `width_mm`, `dash_mm` (บวก = เส้น, ลบ = ช่องว่าง แบบไฟล์ .lin), `pattern`, `colour`, `label`
- `hatch_pattern`: ลวดลายแรเงา (ลวดลายไทยยังไม่ทราบ จึงเป็น `unknown`)
- `redraw_description {th, en}`: คำอธิบายสำหรับวาดใหม่ (บังคับทุกระเบียน) และเป็นที่มาของคอลัมน์ `geometry_summary_th` ใน CSV

## 6. ชุดคำศัพท์และการแก้ปัญหารหัสชนกัน

- `tag_prefixes` เก็บรหัสแยกตาม **(หมวดงาน, รหัส)** ตัวอย่างรหัสที่ชนกัน:
  - `F` = วัสดุพื้น (ARCH) / ฐานราก (STR)
  - `C` = ฝ้าเพดาน (ARCH) / เสา (STR)
  - `W` = หน้าต่าง (ARCH) / ผนัง ค.ส.ล. (STR) / ท่อน้ำทิ้ง (SAN)
  - `ป` = ประตู (ARCH) / เหล็กปลอก `ป-` (STR)
  - `RB` = คานหลังคา / เหล็กกลม
  - `SD` = อุปกรณ์ตรวจจับควัน (FA) / ลิ้นกันควัน (HVAC) / สวิตช์หรี่ไฟ (ELEC)
  - `FD` = ฟลอร์เดรน (SAN) / ลิ้นกันไฟ (HVAC) / ตรวจจับเปลวไฟ (FA)
- **กฎ:** ค้นรหัสด้วยคู่ (discipline, code) เสมอ ห้ามใช้รหัสอย่างเดียว ระหว่าง ARCH กับ STR ให้ใช้ชุดเลขแผ่นช่วยแยก (A* กับ S*/ST*) ถ้าชนกันในหมวดงานเดียวกัน (เช่น ELEC `M` = มอเตอร์/มิเตอร์) ให้แยกด้วย `id` ของสัญลักษณ์ที่วาง ไม่ใช่ด้วยข้อความ รหัสสถานะ PRACTICE/unverified ให้สำนักงานกำหนดทับได้ในระดับโครงการ
- ชุดคำศัพท์อื่น (เลขแผ่น อักษรย่อท่อ สีท่อ รหัสสาย ท่อร้อยสาย สีสายไฟ เหล็กเสริม เหล็กรูปพรรณ ฯลฯ) มี `status`, `sources`, `standards` แบบเดียวกับระเบียนสัญลักษณ์

## 7. การตรวจสอบและสร้าง CSV

```bash
cd TBIM/data
python3 validate.py          # ตรวจ + สร้าง tbim_symbols.csv ใหม่ (UTF-8 BOM)
python3 validate.py --no-csv # ตรวจอย่างเดียว
```

`validate.py` ใช้ `jsonschema` (ถ้าไม่มีจะลอง `pip install jsonschema` ถ้ายังไม่ได้จะตรวจแบบพื้นฐาน) และตรวจเพิ่ม:
- `id` ไม่ซ้ำ และหมวดงานใน `id` ตรงกับ `discipline`
- ระเบียน `TH.*` มีโปรไฟล์ TH
- ทุกระเบียน/โปรไฟล์/รายการคำศัพท์มี URL หรือ `source_note`
- `related_ids`, `used_by`, `collides_with` อ้างถึงรายการที่มีอยู่จริง
- regex คอมไพล์ได้ และตัวอย่างทุกตัว match
- `object_type` ของ IfcAnnotation เท่ากับ `id`
- **URL แหล่งที่มาทุกตัวต้องปรากฏในบันทึกการค้นคว้า** (ถ้าพบโฟลเดอร์บันทึก)

ถ้าผ่านจะจบด้วย `OK: catalog is valid` (exit code 0)

## 8. วิธีเพิ่มหรือแก้ไขข้อมูล

1. แก้ `tbim_symbols.json` โดยตรง (ไฟล์เป็น UTF-8, indent 2) แล้วรัน `python3 validate.py` ทุกครั้ง
2. **สัญลักษณ์ใหม่:** ตั้ง `id` ใหม่ตามรูปแบบ `TH.<DISC>.<NAME>` (ใช้ `INTL.` เฉพาะแนวคิดที่ไม่มีคู่เทียบในไทย) ใส่โปรไฟล์ `TH` เสมอ แล้วเพิ่มรูปแบบต่างประเทศเป็น `region_profiles` ของระเบียนเดียวกัน **อย่าสร้างระเบียนแยก** ถ้าเป็นแนวคิดเดียวกัน
3. **ยืนยันข้อมูล:** เมื่อเปิดอ่าน PDF ใน `verify_against` ได้ (เช่น แผ่นสัญลักษณ์ ops.go.th, smpkhos.go.th, คู่มือ ASA 2549/2554, คู่มือการเขียนแบบวิศวกรรมงานทาง 2558 ของกรมทางหลวง) ให้ปรับ `status`, เพิ่ม `sources` (evidence = `full_text`), ใส่ขนาดจริงใน `nominal_size_mm` (`size_basis: "source"`) และ `svg_path` (`svg_basis: "notes"`) แล้วเพิ่ม `version`
4. **แหล่งที่มาใหม่:** `validate.py` บังคับว่า URL ต้องอยู่ในบันทึกการค้นคว้า ถ้าจะเพิ่มแหล่งใหม่ ให้เพิ่มลงในไฟล์บันทึก (หรือบันทึกฉบับใหม่ในโฟลเดอร์เดียวกัน) ก่อน
5. **มาตรฐาน:** ใส่เลขมาตรฐานตามที่ปรากฏในเอกสารต้นฉบับเท่านั้น ห้ามเดาเลข/ปี
6. **ระบบจัดหมวด:** ใส่ใน `classification[]` เช่น `{system: "Uniclass 2015", table: "Ss", code: "..."}` หรือ URI ของ bSDD Uniclass เป็น CC BY-ND 4.0 **ห้ามเพิ่มรหัสไทยลงในตาราง Uniclass** ให้ใช้ namespace ของ TBIM (`TBIM-SYM`) แล้ว map ไป
7. ห้ามแก้ `tbim_symbols.csv` ด้วยมือ ให้รัน `validate.py` สร้างใหม่

## 9. ข้อจำกัดและข้อควรระวัง

- **ขนาดสัญลักษณ์ของไทยยังไม่ทราบ:** แผ่นสัญลักษณ์ในคู่มือ ASA มาตรฐานการเขียนแบบก่อสร้าง 2549/2554 เปิดอ่านไม่ได้ ค่า Ø10 มม. ของวงกลมอ้างอิงและหัวกริดเป็นค่าเริ่มต้นที่ TBIM เสนอ (ใกล้เคียง Bonsai 10 มม. และ GB 8–10 มม.) ไม่ใช่มาตรฐานไทย
- **MEP ทั้งหมดยังไม่ยืนยัน:** ต้องตรวจกับแผ่นสัญลักษณ์ของหน่วยงานไทยที่ระบุใน `verify_against`
- **`host_ifc_classes` เป็นข้อเสนอของ TBIM** (เช่น IfcOutlet, IfcSensor) ไม่ได้มาจากบันทึก ต้องตรวจกับเอกสาร IFC4.3 ชื่อ IfcDraughtingPreDefinedCurveFont ก็ยังไม่ยืนยัน
- **ข้อมูลที่ขัดกันเองในบันทึก** (เก็บไว้ในหมายเหตุ):
  - การระบายสีตู้ไฟ: ไทย "ติดลอย = ทึบ, ฝัง = ทึบครึ่ง" แต่ NECA "ฝัง = ทึบ, ติดลอย = โปร่ง"
  - ความกว้างเส้นจราจร 10 ซม. ในข้อมูลผู้ขายไม่ชัดว่าใช้กับเส้นใด
  - ผังบริเวณ 1:750 ในชุดแบบจริงขัดกับกฎ ≥1:500
  - ปีฉบับของ ISO 7519 (2024/2025/"2026")
  - สถานะของ ISO 4067-1
  - ข้อความ "ทรงกระบอก 240 = ลูกบาศก์ 210" ผิดหลักฟิสิกส์ จึงไม่ได้นำเข้า
- **ยังไม่มีข้อมูล:**
  - รูปทรงลูกศรทิศเหนือแบบไทย (ใช้รูปแบบ GB เป็นค่าเริ่มต้น)
  - match line, scale bar, สามเหลี่ยมเลขแก้ไข, สัญลักษณ์ต้นไม้
  - ลวดลายแรเงาวัสดุของไทย
  - legend ของ L7018 และสัญลักษณ์ในคู่มือกรมทางหลวง
  - รายการ "UGX" ในแผ่น A0-01 ไม่ทราบความหมาย จึงไม่ได้นำเข้า
- ตัวอย่างใน `notation_grammar` ที่แต่งขึ้น (เช่น ตัวเลขใบอนุญาต ระยะสถานี) มี `examples_note` ระบุไว้
